Technical logging

I expect you to produce a persistent log file that records errors and diagnostically useful
events during my manual testing, your builds, and your autonomous runs.

The logging system must capture as much useful diagnostic information as reasonably
possible without noticeably impacting game performance.

Each relevant log entry should include, where applicable:

     Exact date and time, including seconds and preferably milliseconds.
     Log severity: TRACE, DEBUG, INFO, WARNING, ERROR, FATAL.
     Build/version identifier and Git commit if available.
     Current game/session ID.
     Current tick/frame number where relevant.
     Subsystem, class, source file and function/method name.
     Call stack/stack trace for errors and exceptions.
     Exception type and full exception message.
     Function execution duration when unusually slow or when an error occurs.
     Important arguments passed to the failing function, excluding huge objects or

         sensitive data.
     Relevant game state surrounding the failure.
     Current map/location identifier.
     Relevant pawn/entity/object IDs.
     Player or automated action immediately preceding the event.
     State transitions, such as entering/leaving maps, loading/saving games, generating

         worlds, spawning/despawning entities, etc.
     Failed assertions and violated invariants.
     Save/load errors and serialization/deserialization problems.
     Resource loading failures.
     Physics, pathfinding, AI, simulation and rendering errors when applicable.
     Random/world seed when relevant for reproducing procedural-generation bugs.
     Correlation/event ID so related operations can be followed through multiple functions.

For serious errors, include enough surrounding context to reconstruct what happened
immediately before the failure.

The logger must flush critical/error entries immediately so crashes do not erase the useful
information.

Use rotating log files with maximum size/age limits so logging cannot indefinitely consume
disk space.

Normal gameplay logging must remain lightweight. Do not continuously serialize large game
states, dump complete objects, produce stack traces for normal operations, or log every
frame/tick.

A more verbose diagnostic mode may be enabled during automated testing when additional
information is useful.

Do not use defensive programming to conceal bugs. Specifically avoid:

     Empty or silent catch blocks.
     Catching every exception with a generic catch unless it is logged and

         rethrown/handled deliberately.
     Returning arbitrary default values after unexpected failures.
     Automatically repairing corrupted or invalid state without reporting it.
     Excessive null-check/fallback chains that hide incorrect program state.
     Retrying failed operations indefinitely.
     Suppressing assertions merely to keep the game running.
     Logging an error and then continuing as though the operation succeeded.
     Duplicating the same error through many layers of the call stack.
     Expensive logging inside tight loops, per-frame code, physics iterations, or large

         entity loops.

Use defensive checks where they protect against genuinely expected runtime conditions, but
unexpected internal states should fail visibly, produce useful diagnostics, and make the
underlying bug easy to identify rather than masking it.

Prefer explicit invariants, assertions, validation at system boundaries, deterministic
behaviour, and errors that fail close to their actual source.

Efficiency

Treat performance as a fundamental requirement throughout development, not something to
address only at the end.

Assume the final game should run fluidly on a machine roughly **half as powerful as mine**.

Execution Speed and FPS

Execution speed and stable FPS are paramount.

The final goal is to support very large simulations, with hundreds of actively simulated
entities locally and potentially thousands to millions represented at the planetary scale.

Design systems from the beginning with scalability in mind. Use appropriate modern
techniques, algorithms, data structures, parallelism, caching, batching, level-of-detail
simulation, profiling, and other optimisation methods whenever they provide meaningful
gains.

Do not sacrifice the visual quality or simulation depth I request merely because an inefficient
implementation cannot handle them. Look for a better implementation first.

Use C++ wherever it provides substantial performance benefits, particularly for
computationally intensive systems. Do not use C++ merely for the sake of using C++ when
another approach performs sufficiently well and is easier to maintain.
When working in C++, proactively account for the usual problems associated with native
code, including memory, lifetime, concurrency, undefined behaviour and crashes. Use the
appropriate modern debugging, profiling, diagnostic and testing tools available at the time
rather than relying only on manual inspection.

If a crash, slowdown, memory problem or instability appears, investigate its root cause using
logs, profilers, debuggers, sanitizers or whatever equivalent tools are appropriate for the
current environment.

Avoid hiding problems with defensive workarounds that merely prevent the visible failure
while leaving the underlying defect unresolved.

Profile before making major low-level optimisations. Prioritise real bottlenecks rather than
guessing which code is expensive.

Prefer scalable architecture over micro-optimisations when the architectural improvement
provides a larger gain.

Memory

Keep memory consumption efficient and avoid unnecessary allocations, duplication, retained
objects and unnecessarily large data structures.

Do not keep data in memory when it is not needed, and choose representations appropriate
to the scale of the simulation.

However, do not sacrifice substantial execution speed merely to save a small amount of
memory. Runtime performance and stable FPS have higher priority unless memory
consumption itself becomes a bottleneck.

Continuously monitor both performance and memory usage during development and
automated testing, and adapt the implementation when profiling shows that a different
approach would perform better.

Planet environment

The core concept

Planetary and Local Map Synchronization

The planetary view and every playable location must be part of the same simulation system.

What happens at the planetary level must also affect the currently selected playable location,
whether that location is a colony, a caravan, a temporary encounter map, or any other
playable map.

The planetary view must therefore not be a separate abstract representation disconnected
from local gameplay. Instead, it must represent the large-scale environmental state from
which local maps derive their natural conditions.

Planetary Environmental Views

In addition to the normal biome map already present in the base game, the planetary view
must provide buttons allowing the player to display additional environmental maps and
heatmaps.

At minimum, these must include:

    1. Temperature Heatmap
         Displays the geographical distribution of natural ambient temperature across the
         entire planet.

    2. Landscape / Elevation Map
         Displays planetary elevation and terrain height, including lowlands, plains, hills,
         mountain ranges, high plateaus, depressions, and other major elevation differences.

    3. Moisture / Precipitation Map
         Displays the distribution of environmental moisture and precipitation across the
         planet.

These maps are not merely visual overlays. Their values must correspond to actual
environmental conditions used by the simulation.

Connection Between Planetary Conditions and Playable Maps

Planetary environmental values must directly influence every playable map located on the
planet.

For example, if the planetary temperature map indicates that a certain region currently has a
natural ambient temperature of 32°C, a playable map located in that region must use
approximately that temperature as its undisturbed outdoor environmental temperature.

The same principle applies to moisture and precipitation.
A region experiencing high precipitation or moisture at the planetary level must experience
corresponding conditions on its playable maps, such as rainfall, snow, soil moisture,
humidity, water accumulation, vegetation effects, or any other systems affected by
precipitation.

Changes occurring on the planetary environmental maps must therefore propagate to the
relevant playable maps.

Dynamic Planetary Conditions

Temperature, moisture, and precipitation must be dynamic rather than permanently fixed
values.

They must evolve naturally during gameplay according to planetary conditions such as:

     Seasons
     Latitude
     Time of year
     Elevation
     Weather systems
     Regional climate
     Natural climate variation

The planetary environmental maps must update as these conditions change.

Playable maps must remain synchronized with those changes.

For example, if seasonal changes cause the planetary temperature of a region to fall from
15°C to -5°C, playable maps located within that region must experience the corresponding
seasonal cooling.

Likewise, if a region enters a wetter seasonal period, the increased planetary precipitation
must be reflected locally.

Natural Ambient Temperature

The temperature displayed on the planetary heatmap must represent the natural
undisturbed ambient temperature of the region.

It must not represent an absolute minimum or maximum temperature that cannot be
exceeded.

Local conditions may cause temperatures to become either higher or lower than the
planetary ambient temperature.

For example:

     A refrigerated room may be much colder than the planetary ambient temperature.
     A heated room may be significantly warmer.
     A forest fire may create extremely high local temperatures.
     Lava, magma, or hydrothermal vents may produce temperatures far above the
         regional ambient temperature.

     Artificial cooling systems may create environments far colder than surrounding
         conditions.

     Underground areas may have temperatures different from surface conditions.
     Buildings and insulation may modify internal temperatures.

The planetary heatmap therefore defines the baseline natural environmental
temperature, not a hard temperature limit.

In simplified terms:

Planetary temperature = local natural outdoor baseline temperature

Local simulation systems may then modify this value according to terrain, structures,
weather, heat sources, cooling sources, underground conditions, and other environmental
effects.

Persistent Environmental Link

Every playable map must retain its geographical relationship with the planetary simulation.

A local map must know where on the planet it is located and retrieve the appropriate
planetary environmental values for that position.

This applies to:

     Permanent colonies
     Settlements
     Caravans
     Temporary encounter maps
     Quest locations
     Wilderness maps
     Generated combat locations
     Any other playable location situated on the planet

This ensures that the player is always experiencing the same planet at different scales rather
than switching between disconnected planetary and local simulations.
